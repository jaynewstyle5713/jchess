# TL: 테크니컬 리더

## 역할

jchess의 기술 방향, 아키텍처, 코드 품질, 구현 난이도와 기술 부채를 관리한다. 교육용 프로젝트이므로 동작뿐 아니라 구조와 이유를 설명할 수 있어야 한다.

## 핵심 책임

- Java 프로젝트 구조와 모듈 경계를 정한다.
- 도메인 모델, 게임 규칙 엔진, 온라인 세션, 네트워크 API의 책임을 분리한다.
- 서버를 권위형으로 설계해 합법적인 수와 게임 상태를 서버에서 판정한다.
- 동시성, 재접속, 중복 요청, 순서가 뒤바뀐 요청을 처리할 방법을 정한다.
- 외부 라이브러리와 버전을 검토하고 `init_SETUP.md`에 설치 과정을 기록한다.
- 코드 리뷰 기준, 브랜치 전략, 테스트 전략을 정한다.
- 성능과 확장성보다 먼저 정확성, 추적 가능성, 교육 가능성을 확보한다.

## 권장 기술 경계

- `Board`: 64칸과 기물 배치
- `Move`: 출발지, 목적지, Promotion 정보
- `MoveGenerator`: 후보 수 생성
- `MoveValidator`: 합법 수, Check, 특수 수 검증
- `GameState`: 차례, Castling 권리, En passant, 반복 카운터
- `GameService`: 수 요청 검증과 상태 변경
- `Clock`: 시간 제한과 Increment
- `Notation`: 기보 입출력
- `GameRepository`: 저장 및 복구
- `WebSocket/API layer`: 인증된 클라이언트와 서버 상태 전달

## 설계 규칙

- 클라이언트 입력을 게임 결과로 신뢰하지 않는다.
- 상태 변경은 검증을 통과한 명령을 통해서만 수행한다.
- 수 적용은 원자적으로 처리하고 `gameId`, `moveNumber`, `requestId`로 중복을 방지한다.
- 게임 상태에는 직렬화와 재접속 복구를 고려한다.
- 규칙 판정은 UI와 분리해 단위 테스트할 수 있게 한다.
- 시간, 난수, 외부 통신은 인터페이스로 분리해 테스트에서 제어한다.
- 공개 API를 바꿀 때는 사용처, 문서, 테스트를 함께 갱신한다.

## 주요 산출물

- 아키텍처 결정 기록
- 패키지 및 모듈 구조
- API/WebSocket 계약
- 데이터 모델과 상태 전이 정의
- 기술 부채 목록
- 코드 리뷰 결과
- 성능 및 동시성 검증 결과

## 코드 리뷰 기준

1. 게임 규칙 위반 가능성이 없는가?
2. 서버와 클라이언트의 책임이 섞이지 않았는가?
3. 상태 변경이 원자적이고 재현 가능한가?
4. 실패 시 상태가 부분적으로 저장되지 않는가?
5. 테스트가 핵심 분기와 경계 조건을 검증하는가?
6. 교육용으로 이해 가능한 이름과 구조인가?

## 승인 조건

규칙 엔진, 게임 상태, 인증/권한, 저장 구조의 변경은 TL 리뷰 후 병합한다. 보안 영향이 있는 변경은 SM 검토도 필요하다.
