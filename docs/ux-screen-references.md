# 온라인 체스 UX 화면 레퍼런스

## 1. 목적

이 문서는 UX/UDI 담당자가 jchess의 기본 온라인 체스 화면을 기획할 때 참고할 대표 서비스의 실제 화면과 관찰 포인트를 정리한다.

참고 화면은 그대로 복제하기 위한 것이 아니다. 레이아웃, 정보 우선순위, 상호작용과 상태 피드백을 비교하고 jchess에 맞는 설계 원칙을 도출하기 위한 자료다.

## 2. 저작권 및 사용 원칙

- 아래 링크는 각 서비스의 공식 페이지다.
- 이 저장소에는 타 서비스의 화면 이미지를 복제하거나 배포하지 않는다.
- 기획 문서에는 공식 URL과 조사 날짜를 기록한다.
- 발표나 교육 자료에 실제 화면 캡처를 넣을 경우 서비스의 이용 약관, 저작권, 상표 정책을 확인하고 출처를 표시한다.
- 최종 제품 UI는 관찰한 문제를 해결하는 독자적인 디자인으로 제작한다.

조사일: 2026-09-08

## 3. 화면 레퍼런스 5종

### 3.1 Chess.com 온라인 대국 화면

- 공식 화면: [Chess.com Play Online](https://www.chess.com/play/online)
- 확인 가능한 요소:
  - 중앙 체스보드
  - 상단과 하단 플레이어 영역
  - 양쪽 플레이어 시계
  - 보드 좌표
  - 새 게임, 친구 초대, 시간 형식 선택
  - 현재 접속자와 게임 수 등 서비스 진입 정보
- 관찰 포인트:
  - 게임 시작 전 설정과 실제 대국 화면을 한 흐름으로 연결한다.
  - 시계와 플레이어 정보를 보드 주변의 고정 영역에 배치한다.
  - 초보자가 바로 게임을 시작할 수 있도록 시간 형식을 선택지로 제공한다.
- jchess 적용 후보:
  - 게임 시작 화면에서 시간 형식과 상대 초대 제공
  - 현재 차례의 시계를 시각적으로 강조
  - 모바일에서 보드와 시계가 겹치지 않는 반응형 배치

### 3.2 Lichess 분석 보드 화면

- 공식 화면: [Lichess Analysis Board](https://lichess.org/analysis)
- 확인 가능한 요소:
  - 체스보드와 좌표
  - FEN 및 PGN 정보
  - Standard 변형 선택
  - 분석 엔진 상태
  - 보드 아래 또는 주변의 수와 포지션 정보
  - Blind mode 등 접근성 진입점
- 관찰 포인트:
  - 대국용 보드와 분석용 보드는 목적이 다르므로 정보 밀도를 분리한다.
  - FEN/PGN처럼 전문 기능은 초보자 화면의 기본 영역과 분리할 수 있다.
  - 접근성 모드를 서비스 메뉴에서 명시적으로 제공한다.
- jchess 적용 후보:
  - MVP 대국 화면에는 보드, 시계, 마지막 수, 연결 상태만 우선 노출
  - 기보와 분석 정보는 확장 패널로 분리
  - 키보드 탐색과 보조기술용 기물 이름 제공

### 3.3 Chess.com 게임 분석 및 Game Review 화면

- 공식 화면: [Chess.com Game Review and Analysis](https://www.chess.com/analysis)
- 관련 학습 화면: [Chess.com How To Play Chess](https://www.chess.com/article/view/how-to-play-chess)
- 확인 가능한 요소:
  - 수를 한 단계씩 재생하는 분석 흐름
  - 좋은 수, 실수, 놓친 기회 같은 평가 정보
  - 변형 수와 복기 목적의 화면 구조
  - Checkmate, Stalemate, Castling, En passant 등 규칙 학습 링크
- 관찰 포인트:
  - 게임 종료 후 결과 화면과 학습/복기 화면은 분리된 사용 목적을 가진다.
  - 복잡한 평가 정보는 수 자체를 이해하는 흐름을 방해하지 않도록 단계적으로 노출해야 한다.
  - 초보자에게는 규칙 용어에 대한 설명 진입점이 중요하다.
- jchess 적용 후보:
  - MVP에서는 기보 재생과 게임 결과만 제공
  - 엔진 평가와 자동 코칭은 후속 릴리스로 분리
  - 용어 설명을 보드 위에 상시 표시하지 않고 도움말로 제공

### 3.4 Lichess 빠른 대국 및 로비 진입 화면

- 공식 화면: [Lichess](https://lichess.org/)
- 확인 가능한 요소:
  - Quick pairing
  - Bullet, Blitz, Rapid, Classical 시간 형식
  - Custom, Lobby, 친구 도전
  - 현재 플레이어와 진행 중 게임 수
  - Play against computer와 학습 진입점
- 관찰 포인트:
  - 사용자가 시간 형식을 고르는 경로가 짧다.
  - 빠른 대국, 사용자 지정 대국, 친구 도전의 목적을 분리한다.
  - 서비스의 커뮤니티 기능과 대국 시작 기능이 같은 진입점에 존재한다.
- jchess 적용 후보:
  - MVP는 `빠른 대국`, `친구 초대`, `사용자 지정` 세 가지로 단순화
  - 대국 형식과 예상 소요 시간을 함께 표시
  - 매칭 대기, 상대 연결, 취소 상태를 명확히 표시

### 3.5 Lichess 토너먼트 화면

- 공식 화면: [Lichess Tournaments](https://lichess.org/tournament)
- 관련 커뮤니티 화면: [Lichess Streamers](https://lichess.org/streamer)
- 확인 가능한 요소:
  - 진행 중 토너먼트 목록
  - 시간 형식과 진행 상태
  - 참가자와 순위 중심의 정보
  - 커뮤니티 활동으로 이동하는 링크
- 관찰 포인트:
  - 반복 대국을 위한 목록형 정보는 보드 화면과 다른 밀도와 우선순위를 가진다.
  - 진행 상태, 시작 시간, 참가 규모를 목록에서 빠르게 비교한다.
  - 커뮤니티 기능은 개인 대국과 분리된 탐색 영역으로 제공한다.
- jchess 적용 후보:
  - 토너먼트는 MVP 이후 기능으로 분리
  - 목록 화면에는 상태, 시간 형식, 참가 가능 여부를 우선 표시
  - 대국 화면과 토너먼트 탐색 화면의 내비게이션을 분리

## 4. 공통 패턴과 차이점

### 공통 패턴

- 보드는 화면의 가장 중요한 시각적 대상이다.
- 플레이어 정보와 시계는 보드 가까이에 고정한다.
- 현재 차례와 연결 상태를 즉시 알 수 있어야 한다.
- 마지막 수와 수 기록은 복기에 필요한 핵심 정보다.
- 빠른 대국과 사용자 지정 대국을 구분한다.

### 차이점

| 관점 | Chess.com | Lichess | jchess 방향 |
| --- | --- | --- | --- |
| 기본 진입 | 게임 시작과 콘텐츠 진입을 함께 제공 | 빠른 대국과 로비 선택이 명확함 | MVP는 대국 시작을 가장 짧게 구성 |
| 분석 | Game Review와 학습 콘텐츠 연결 | 분석 보드와 FEN/PGN 기능이 강함 | 기보 재생부터 시작, 엔진은 후순위 |
| 정보 밀도 | 초보자 친화적 선택과 안내 | 숙련자용 도구와 커뮤니티가 풍부함 | 초보 기본 화면과 고급 패널 분리 |
| 접근성 | 학습 콘텐츠와 화면 안내 중심 | Blind mode 등 명시적 진입점 | 키보드와 스크린 리더를 MVP부터 고려 |
| 커뮤니티 | 플레이어/콘텐츠/토너먼트 | 로비/토너먼트/팀/스트리머 | 커뮤니티 기능은 대국 안정화 후 추가 |

## 5. jchess 기본 대국 화면 기획안

### 첫 화면 정보 우선순위

1. 현재 게임 상태: 대기, 내 차례, 상대 차례, 종료
2. 체스보드와 좌표
3. 두 플레이어 이름, 색상, 시계
4. 마지막 수와 간단한 기보
5. 연결 상태 및 재접속 안내
6. 기권, 무승부, 설정 등 보조 작업

### 필수 상태

- `MATCHING`: 상대를 찾는 중
- `WAITING_FOR_OPPONENT`: 상대 입장 대기
- `YOUR_TURN`: 내 차례
- `OPPONENT_TURN`: 상대 차례
- `CHECK`: King이 공격받는 상태
- `PROMOTION_REQUIRED`: Promotion 선택 대기
- `RECONNECTING`: 연결 복구 중
- `CHECKMATE`, `STALEMATE`, `DRAW`, `RESIGNED`, `TIMEOUT`: 종료 상태

화면 상태와 서버 상태를 혼동하지 않는다.

| 화면 상태 | 서버/연결 상태 조합 |
| --- | --- |
| `YOUR_TURN` | `gameStatus=ACTIVE`, `turn=WHITE/BLACK`, 내 색상과 일치 |
| `OPPONENT_TURN` | `gameStatus=ACTIVE`, `turn`이 상대 색상 |
| `CHECK` | `gameStatus=CHECK` |
| `PROMOTION_REQUIRED` | `pendingPromotion`이 존재 |
| `RECONNECTING` | `connectionStatus=RECONNECTING` 또는 `SYNCING` |

서버의 canonical state는 [architecture.md](architecture.md)의 `gameStatus`, `turn`, `pendingPromotion`, `connectionStatus`, `gameVersion`을 따른다.

### 금지할 설계

- 색상만으로 Check 또는 현재 차례를 표현하지 않는다.
- 서버 확정 전 수를 최종 결과처럼 표시하지 않는다.
- 모바일 화면에서 시계와 보드를 겹치게 배치하지 않는다.
- 초보자 대국 중 분석 엔진, 복잡한 통계, 광고성 요소를 기본 화면에 과도하게 노출하지 않는다.
- 기존 서비스의 로고, 색상 체계, 아이콘, 화면을 그대로 복제하지 않는다.

### 접근성 및 반응형 수용 기준

- 목표 기준: WCAG 2.2 AA.
- 보드는 8 x 8 키보드 탐색 영역으로 제공하고 화살표 키로 칸을 이동하며 Enter/Space로 선택과 수 확정을 수행한다.
- 선택된 칸, 가능한 목적지, Check 상태는 색상 외에 포커스 테두리, 아이콘 또는 텍스트로 구분한다.
- 수 확정, 수 거부, 차례 변경, Check, Checkmate, 재접속, timeout은 `aria-live` 상태 영역으로 알린다.
- Promotion 선택은 기물 이름을 읽을 수 있는 버튼으로 제공하고 선택 후 포커스를 보드의 도착 칸으로 복원한다.
- 수 거부 시 포커스를 오류 메시지 또는 원래 선택된 칸으로 이동하고, 원인과 재시도 방법을 제공한다.
- 최소 터치 영역은 44 x 44 CSS px로 한다.
- 지원 범위는 최신 주요 브라우저 2개 버전과 최소 360 x 640 CSS px viewport이며, 세로 화면에서 가로 스크롤 없이 핵심 대국을 수행한다.
- `prefers-reduced-motion`이 활성화되면 기물 이동 애니메이션을 줄이거나 제거한다.

### 상태 및 오류 문구 기준

서버 오류 코드는 사용자 문구와 분리한다.

| 코드 | 사용자 문구 방향 | 복구 행동 | 중요도 |
| --- | --- | --- | --- |
| `GAME_VERSION_CONFLICT` | 최신 게임 상태를 불러왔습니다. | 최신 보드로 동기화 | 안내 |
| `MOVE_NOT_LEGAL` | 이 수는 둘 수 없습니다. | 다른 기물/칸 선택 | 경고 |
| `NOT_YOUR_TURN` | 지금은 상대의 차례입니다. | 대기 | 안내 |
| `GAME_ALREADY_FINISHED` | 게임이 이미 종료되었습니다. | 결과 확인 | 안내 |
| `RECONNECTING` | 연결을 복구하는 중입니다. | 자동 재연결 대기 | 경고 |
| `SYNC_FAILED` | 게임 상태를 불러오지 못했습니다. | 재시도 또는 나가기 | 오류 |

## 6. UX 기획 단계

### UX-01: 대상과 핵심 시나리오 정의

- 대상: 체스를 처음 배우는 사용자와 기본 규칙을 아는 온라인 대국 사용자
- 시나리오:
  - 빠른 대국 시작
  - 친구 초대 대국
  - 수 선택과 확정
  - Promotion 처리
  - Checkmate 또는 무승부 종료
  - 연결 끊김 후 재접속
- 산출물: 사용자 시나리오, 용어집, 성공 기준

### UX-02: 레퍼런스 비교와 요구사항 추출

- 위 5개 화면에서 공통 요소와 차이점을 비교한다.
- 요소를 `MVP 필수`, `후속 기능`, `참고만 함`으로 분류한다.
- 산출물: 레퍼런스 비교표, MVP UX 요구사항
- 빠른 대국, 친구 초대, 사용자 지정은 MVP 대국 생성/참가 흐름에서 우선 검토하되 토너먼트와 커뮤니티는 후속으로 분류한다.

### UX-03: 정보 구조와 상태 모델 설계

- 보드, 플레이어, 시계, 기보, 연결 상태의 우선순위를 정한다.
- 서버 게임 상태와 화면 표시 상태를 매핑한다.
- 오류, 재접속, 게임 종료 상태를 정의한다.
- 산출물: 화면 상태표, 정보 구조, 상태 전이도

### UX-04: 저해상도 와이어프레임

- 데스크톱과 모바일의 기본 대국 화면을 설계한다.
- 시작 전, 대국 중, Promotion, Check, 종료, 재접속 화면을 포함한다.
- 산출물: 와이어프레임, 화면별 컴포넌트 목록

### UX-05: API 및 이벤트 계약 협업

- UX 상태를 Backend API와 WebSocket event에 매핑한다.
- 오류 코드가 사용자 메시지로 변환되는 규칙을 정한다.
- 서버 확정 전/후의 UI 상태를 구분한다.
- 산출물: 상태-이벤트 매핑표, 오류 메시지 목록
- `eventId`, `gameId`, `gameVersion`, `eventType`, `occurredAt`, `payload`를 포함한 WebSocket envelope을 사용한다.

### UX-06: 접근성 및 입력 검증

- 키보드, 마우스, 터치 입력을 설계한다.
- 기물과 칸의 접근 가능한 이름을 정의한다.
- 색상 대비, 포커스, reduced motion, 스크린 리더 흐름을 검토한다.
- 산출물: 접근성 체크리스트, 입력 상호작용 규칙
- 키보드 보드 탐색, `aria-live`, 포커스 복원, 44 x 44 CSS px, WCAG 2.2 AA를 체크한다.

### UX-07: 프로토타입과 사용성 테스트

- 최소 3명의 테스트 사용자로 핵심 흐름을 검증한다.
- 측정 항목: 게임 시작 성공률, 잘못된 수 이해도, 현재 차례 인식, 재접속 이해도
- 산출물: 테스트 기록, 문제 목록, 수정 우선순위

### UX-08: 개발 인수와 회귀 검토

- 구현 가능한 디자인 토큰과 컴포넌트 상태를 확정한다.
- QM과 함께 화면 상태별 테스트 시나리오를 작성한다.
- 구현 후 실제 화면이 와이어프레임과 상태 계약에 맞는지 검토한다.
- 산출물: 디자인 인수 문서, 화면 회귀 체크리스트

## 7. 조사 결과의 프로젝트 반영 원칙

- 레퍼런스 조사 결과는 jchess의 독자적인 정보 구조로 변환한다.
- UI 구현 전 UX-01~UX-05를 완료해 API/WebSocket 계약과 충돌하지 않게 한다.
- UX-06은 MVP 릴리스 게이트에 포함한다.
- UX-07은 최소 대국 흐름이 실행된 뒤 진행한다.
- 분석, 토너먼트, 커뮤니티 기능은 기본 대국의 안정성을 해치지 않는 후속 단계로 둔다.
